Workshop Ledger

One HTML file. Everyone adds one row and re-adds the total by hand. Almost nobody gets it right on the first try — and that is exactly what this workshop is for.

1 file to edit 1 CI check branches · commits · pull · push · PRs · conflicts

The ledger

Add your row directly above the Total row, then recompute the total.

Participant Number Notes
Instructor 10 Initial seed
Test Green 5 CI smoke test — safe to delete
Total 15 Sum of the Number column, computed by hand

Rules for your row. The CI enforces the formatting ones — break any of those and your pull request goes red:

  • Exactly three cells per row, in the order Participant, Number, Notes.
  • Pick a number between 1 and 99, so the column stays easy to add by hand once the whole group has joined.
  • The Number cell keeps its class="num" and holds a plain integer — 7, not 7 points, not 3.5, not 1 000.
  • Your row goes above the total row, inside <tbody>.
  • There is exactly one id="total" cell in the whole file. Never duplicate the total row.
  • You must update the total yourself. Nothing on this page computes it for you — on purpose.

Your task

Six steps. Budget about ten minutes; most of it is waiting on other people's pull requests.

  1. Get the repository onto your machine Accept the GitHub invite (or fork), then git clone.
  2. Create your own branch Never work on main. Name it after you, e.g. add-row-ana.
  3. Add your row and pick a number Insert it directly above the Total row.
  4. Re-add the Number column by hand Write the new sum into the total cell. Count every row, not just yours.
  5. Check it locally, then commit and push python scripts/verify_sum.py runs the exact CI check on your laptop.
  6. Open a pull request and resolve the conflict You will hit one. Everybody does. Section below explains why.

Step by step

Open what you need. Every command below is copy-pasteable; replace the values in ALL-CAPS.

1. Get the code

If you were invited as a collaborator (the usual case here), accept the invite email first, then:

git clone https://github.com/darius-f96/mhp-ubb-git-workshop.git
cd mhp-ubb-git-workshop

If you are working from a fork instead, fork on GitHub, then add the original as upstream so you can sync later:

git clone https://github.com/YOUR-USERNAME/mhp-ubb-git-workshop.git
cd mhp-ubb-git-workshop
git remote add upstream https://github.com/darius-f96/mhp-ubb-git-workshop.git

Either way, check where you are:

git status
git log --oneline -5
2. Create your branch

Make sure main is current, then branch off it:

git switch main
git pull
git switch -c add-row-YOURNAME

git status should now say On branch add-row-YOURNAME. A branch is a cheap, independent line of history — creating one costs nothing, and it is what lets twenty people edit the same file at the same time without stepping on each other.

3. Add your row

Open index.html in any editor. Find the marker comment near the bottom of the table body and paste your row directly below it, above the total row:

<tr class="entry-row">
  <td class="name">Your Name</td>
  <td class="num">0</td>
  <td class="notes">anything you want us to know</td>
</tr>

Replace Your Name with your real name and 0 with the number you picked. Notes are optional — leave the cell empty but keep the <td>, otherwise the row has two cells instead of three and the check fails.

Indentation is not decoration here. Match the surrounding rows exactly: the more similar two branches look, the smaller and clearer the conflict will be when they meet.

4. Update the total

Add up every number in the Number column — the seed row, everyone already merged, and you — and write the result into the total cell:

<td id="total">42</td>

This is the part that breaks. Your sum is correct for the file as it looks on your branch right now. By the time your pull request is merged, someone else's row will have landed too, and the total you wrote will be stale. That is not a mistake on your part; it is a property of concurrent work, and it is the lesson.

5. Check it locally

Before you commit, run the same check the CI runs:

python scripts/verify_sum.py

A passing run looks like this:

Ledger: /path/to/index.html

    #  Participant  Number  Notes
    1  Instructor       10  Initial seed
    2  Ana               7  first try

  Rows:             2
  Sum of rows:      17
  Declared total:   17 (line 214)
  Difference:       +0

PASSED - 2 row(s) sum to 17 and the declared total is 17.

Python 3 is the only requirement — the script uses nothing outside the standard library. If python is not found, try python3.

6. Commit and push 
git status                 # what changed?
git diff index.html        # read your own change
git add index.html
git commit -m "Add YOURNAME to the ledger"
git push -u origin add-row-YOURNAME

A commit is a snapshot with a message and a parent. Write the message in the imperative — "Add Ana to the ledger", not "added stuff". Six months from now the log is the only record of why the file looks the way it does.

The -u on the first push links your branch to its copy on GitHub, so later you can just type git push.

7. Open the pull request

After the push, GitHub prints a link — open it. Or go to the repository and click Compare & pull request. Fill in the title, create it, then watch the Verify Ledger Sum check run.

Two outcomes are both useful:

  • Green — your branch adds up on its own. Wait for it to be merged.
  • Red — read the log. It names the row that is malformed or the amount the total is off by.

Once your PR is merged, your job is not finished — see step 8, because everyone else merging after you invalidates your total.

8. Sync with main and resolve the conflict

Other people keep merging while you work. Pull their changes into your branch:

git switch main
git pull
git switch add-row-YOURNAME
git merge main

If two of you inserted a row in the same place, Git refuses to guess and stops:

Auto-merging index.html
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix the conflict and then commit the result.

Find out what is unresolved, open the file, and look for the conflict markers:

git status
git diff

This is what the conflict really looks like — one hunk, not two, because your row and the total row are neighbours:

          <tr class="entry-row">
<<<<<<< HEAD
            <td class="name">Ana</td>
            <td class="num">7</td>
            <td class="notes">first try</td>
          </tr>
          <tr class="total-row">
            <td>Total</td>
            <td id="total">17</td>
=======
            <td class="name">Mihai</td>
            <td class="num">5</td>
            <td class="notes">hello</td>
          </tr>
          <tr class="total-row">
            <td>Total</td>
            <td id="total">15</td>
>>>>>>> add-row-mihai
            <td class="notes">Sum of the Number column, computed by hand</td>
          </tr>

Read HEAD as "what my branch says" and add-row-mihai as "what everyone else decided". Everything between the markers is undecided and it is your job to decide it.

The trap. Two lines sit outside the markers: the opening <tr class="entry-row"> at the top and the closing <td class="notes">Sum of… plus </tr> at the bottom. Git kept them because both sides agreed on them — they appear once, not once per side.

So the reflex move — delete the three marker lines, keep everything else — leaves you with two cells carrying id="total", one row whose opening tag was consumed by the row above it, and HTML that will not render. The check catches it, but it is worth knowing why.

What the region should look like once you are done — two complete participant rows, then one total row:

          <tr class="entry-row">
            <td class="name">Ana</td>
            <td class="num">7</td>
            <td class="notes">first try</td>
          </tr>
          <tr class="entry-row">
            <td class="name">Mihai</td>
            <td class="num">5</td>
            <td class="notes">hello</td>
          </tr>
          <tr class="total-row">
            <td>Total</td>
            <td id="total">22</td>
            <td class="notes">Sum of the Number column, computed by hand</td>
          </tr>

Note what happened to the total. Ana's side said 17 and Mihai's side said 15, and neither is right: 17 counted Ana but not Mihai, 15 counted Mihai but not Ana. The answer is 10 + 7 + 5 = 22, a value that appears on no side of the conflict. You cannot choose your way out of this one; you have to recompute it. That is the whole workshop in one line.

Never leave a marker behind. A stray <<<<<<< in the file is committed HTML that a browser will render as text. Before you finish, search the file for <<<<, ==== and >>>> and make sure none remain.

Then verify and finish:

python scripts/verify_sum.py
git add index.html
git commit                 # closes the merge; the message is pre-filled
git push

Prefer rebasing? git rebase main instead of git merge main, resolve the same conflict, then git add index.html && git rebase --continue. Your pull request will need git push --force-with-lease afterwards. Rebase rewrites history, so only do it on your own branch — never on main.

To abandon a merge that has gone wrong: git merge --abort puts the working tree back the way it was and lets you start over.

Working from a fork instead?

Same workflow, two differences. Sync from upstream rather than origin:

git fetch upstream
git switch add-row-YOURNAME
git merge upstream/main

And when you open the pull request, set base to darius-f96/mhp-ubb-git-workshop : main and compare to YOUR-USERNAME : add-row-YOURNAME.

Why the total keeps being wrong

The single idea this workshop exists to teach.

Git merges text, not meaning. It compares lines and, when two branches changed different lines, it combines them confidently and correctly. It has no idea that one of those lines is a sum of the others.

So this sequence is completely normal and produces a broken file:

  1. main has one row: 10. Total: 10.
  2. Ana branches, adds 7, writes total 17. Her check passes.
  3. Mihai branches from the same main, adds 5, writes total 15. His check passes too.
  4. Ana merges. The file has two rows and total 17. Still correct.
  5. Mihai merges. Git adds his row without a complaint — or raises a conflict he resolves by keeping his own total. The file now has three rows summing to 22 and a total of 17 or 15.

Every individual step was reasonable. The result is wrong. This is why projects have automated checks that run after integration, not only before it.

The fix is always the same: pull the latest main into your branch, re-add the Number column, write the new total, run python scripts/verify_sum.py, push. Your pull request re-runs the check automatically.

What the CI check does

.github/workflows/verify-sum.yml runs on every pull request and on every push to main.

It reads index.html, sums the class="num" cells, and compares the result with the value in the id="total" cell. It fails on:

FailureUsually meansBuild
Conflict markers left in the file A merge or rebase was started and never finished. Delete every marker line and keep the content you actually want. red
Declared total ≠ sum of rows You merged someone else's row and did not re-add. The most common case by far. red
Number cell is not a plain integer Units, decimals, spaces or a thousands separator crept in. red
Row does not have exactly three cells A half-deleted row, a leftover from a merge, or an empty Notes cell that was removed entirely instead of being left blank. red
More than one id="total" The total row got duplicated while resolving a conflict. red
Row still says Your Name The template was committed without being edited. red
The same name and number appear twice A duplicated row. Reported as a warning; the sum check usually catches it too. warn

Reading a failing run

On your pull request, open Checks → Verify Ledger Sum → Validate Total. The log names every row it found and tells you the gap:

  Rows:             3
  Sum of rows:      22
  Declared total:   17 (line 214)
  Difference:       -5

FAILED - the declared total is 5 lower than the sum of the rows.

  Most likely cause: two branches were merged and the total was
  never re-added. Git merged the text correctly - it just cannot
  know that the Total row means something.

  Fix: add up the Number column yourself and put the result in
  <td id="total">22</td>, then commit and push again.

The check runs on main as well, not just on pull requests. If someone merges with a broken total, main goes red — a visible, shared signal that integration broke something no single branch did.
